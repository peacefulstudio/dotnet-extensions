# dotnet-extensions v0.5.0

Peaceful.Extensions 0.5.0 ships native .NET 11 builds of all four packages next to the .NET 10 ones, serves an OpenAPI 3.2.0 document on .NET 11, and lets `AddTelemetry` read every `OpenTelemetry` setting from configuration.

## What's new since v0.4.0

### Native .NET 11 builds next to .NET 10

`Peaceful.Extensions.Core`, `Hosting`, `Serilog` and `Telemetry` each ship a `lib/net10.0` and a `lib/net11.0` asset, and NuGet picks the one that matches your project. Until now a `net11.0` project fell back to the `net10.0` build. The Microsoft dependencies follow the target framework:

| Your target | `Microsoft.AspNetCore.OpenApi` | `Microsoft.OpenApi` | Served OpenAPI document |
| --- | --- | --- | --- |
| `net10.0` | 10.0.x | 2.x | 3.1.x |
| `net11.0` | 11.0.x | 3.x | 3.2.0 |

A `net10.0` project sees no framework change and needs only the .NET 10 SDK. Going forward, the packages target every .NET version Microsoft supports, from `net10.0` up.

### OpenAPI 3.2.0 on .NET 11

On `net11.0`, the document that `AddDefaultOpenApi` registers and `MapScalar` serves at `/openapi/v1.yaml` is OpenAPI 3.2.0, the ASP.NET Core 11 default, built on `Microsoft.OpenApi` 3.x. Scalar 2.20.0 rendered the 3.2.0 document in a headless-browser check on `net11.0`; the package now depends on Scalar 2.21.0. If a client generator, gateway or linter in your pipeline does not read OpenAPI 3.2 yet, one line keeps the document on 3.1; see [Upgrading](#upgrading).

### `AddTelemetry` reads the whole `OpenTelemetry` section

`AddTelemetry` used to read only `OpenTelemetry:Endpoint` from configuration, so the service name, version, instance id, gRPC instrumentation switch and trace sampling ratio had to be set in code. It now binds the whole `OpenTelemetry` section before it runs your options action, so all of them can live in `appsettings.json` or in environment variables such as `OpenTelemetry__ServiceName`:

```json
{
  "OpenTelemetry": {
    "Endpoint": "http://otel-collector:4317",
    "ServiceName": "orders-api",
    "ServiceVersion": "1.4.0",
    "ServiceInstanceId": "orders-api-0",
    "EnableGrpcInstrumentation": true,
    "TraceSamplingRatio": 0.25
  }
}
```

```csharp
builder.AddTelemetry(_ => { });
```

A value set in the options action still wins over the same key in configuration. An out-of-range `TraceSamplingRatio` still fails at startup with a message naming `OpenTelemetry:TraceSamplingRatio`. The `OTEL_SERVICE_NAME` environment variable is not read: `service.name` always comes from `ServiceName`.

### Dependency updates

- `Peaceful.Extensions.Telemetry` moves to the OpenTelemetry 1.21.0 line: `OpenTelemetry.Extensions.Hosting`, `OpenTelemetry.Exporter.OpenTelemetryProtocol`, `OpenTelemetry.Instrumentation.AspNetCore` and `OpenTelemetry.Instrumentation.Http` 1.21.0 (were 1.20.1). `OpenTelemetry.Instrumentation.GrpcNetClient` stays at 1.20.1-beta.1.
- `Peaceful.Extensions.Hosting` depends on `Scalar.AspNetCore` 2.21.0 (was 2.18.3) and, on `net10.0`, `Microsoft.AspNetCore.OpenApi` 10.0.15 (was 10.0.14).

## Upgrading

### Breaking: OpenAPI 3.2.0 and `Microsoft.OpenApi` 3.x on `net11.0`

This affects `net11.0` projects only. With 0.4.0 they got the `net10.0` asset, so `Microsoft.OpenApi` 2.x and a 3.1.1 document. With 0.5.0 they get `Microsoft.OpenApi` 3.x and a 3.2.0 document. On `net10.0` nothing changes: the document stays 3.1.x.

To keep a 3.1 document, set the OpenAPI version on the `v1` document that `AddDefaultOpenApi` registers:

```csharp
using Microsoft.AspNetCore.OpenApi;
using Microsoft.OpenApi;

builder.AddDefaultOpenApi("Orders API", "Order management");
builder.Services.Configure<OpenApiOptions>(
    "v1",
    options => options.OpenApiVersion = OpenApiSpecVersion.OpenApi3_1);
```

Code of your own that uses `Microsoft.OpenApi` 2.x types directly must move to the 3.x API.

### `AddTelemetry` now applies every configured `OpenTelemetry` key

Keys under `OpenTelemetry` that 0.4.0 ignored now take effect, so a host carrying stale values for `ServiceName`, `ServiceVersion`, `ServiceInstanceId`, `EnableGrpcInstrumentation` or `TraceSamplingRatio` changes behaviour on upgrade. Before upgrading, check the `OpenTelemetry` section in every configuration source your host loads (`appsettings.*.json`, environment variables, secret stores) and remove or correct what you do not want applied. A value that does not convert to its property's type, such as `TraceSamplingRatio` set to `10%`, now makes `AddTelemetry` throw an `InvalidOperationException` at startup.
